**Planner DM/unread/notification stayed stale after a DJ accepted — root cause found and fixed (2026-08-02):** the final piece of the booking-acceptance realtime failure. The Planner Events half was already fixed (shared `notifyBookingRequestsChanged` invalidator + `subscribeToBookingRequestChanges` on both `recipient_id` and `sender_id`, since realtime filters match a single column); what remained was that after a DJ accepted, the planner's DM preview never changed, no unread highlight appeared, no Messages badge appeared and no notification arrived. **Root cause: `insertBookingAcceptedDmMessageIfNeeded` in `lib/bookingRequests.ts` deduped per *conversation*, not per *booking*.** It inserted the bare `DM_BOOKING_CONFIRMED_MESSAGE` ("Booking confirmed") — a constant identical for every booking — and skipped the insert whenever any row with that text already existed in the conversation. So exactly one acceptance message could ever exist per planner↔DJ DM: the first acceptance inserted, every later acceptance inserted **nothing**. With no `messages` row there was no realtime event, hence no preview change, no unread state and no badge — and because the notification call was gated behind `if (dmResult.inserted && …)`, the planner's notification was swallowed too. All four reported symptoms have this one cause. **Fix:** acceptance now inserts a per-event message via new `formatBookingConfirmedDmMessage(eventName)` in `lib/dm/dmBookingSystemMessages.ts` ("Booking confirmed · <event>"), and the duplicate query matches that per-event text — so dedupe identifies the booking, and a repeat acceptance of the *same* booking is still suppressed. The per-event form is recognised by `isCanonicalDmBookingSystemMessage` and still **displays** as the concise canonical "Booking confirmed" (the event name exists on the stored row purely to make each acceptance distinct — no visible copy change). The planner's notification is now a `booking_update` "Booking accepted" mirroring the existing decline path, and is no longer gated on the DM insert. No polling, no delays, no `router.refresh`, and the working Planner Events reconciliation is untouched. **All temporary investigation instrumentation removed in this same commit:** deleted `lib/diagnostics/realtimeDiagnostics.ts` and `app/components/debug/RealtimeDebugPanel.tsx`, removed both panel mounts from `OnboardingGuard`, and stripped every `rtLog`/`rtLogChannelStatus`/`rtLogBookingPayload` call site along with the `?ftcdebug=realtime` flag — a new regression test asserts none of it can return. New tests: `testBookingAcceptedDmMessageIsScopedToTheBooking`, `testRealtimeInstrumentationIsFullyRemoved`. `npm run build` clean, `npm run test:regressions` all pass. **Live multi-account verification still outstanding** — Isaac needs to confirm on two physical devices that a second acceptance in an existing DM now updates the planner's preview, unread highlight, Messages badge and notification. **iOS overscroll clipped the fixed bottom nav on Home-button iPhones (2026-08-02):** reported on iPhone SE — rubber-banding past the top or bottom briefly showed the fixed header/bottom nav as clipped. **Cause:** the bottom nav is `position: fixed`, so it is anchored to the *layout* viewport; an iOS bounce moves the *visual* viewport past the layout viewport and the bar stops tracking the physical screen edge. Home-button devices are worst hit because `safe-area-inset-bottom` is 0 there, so the bar already sits flush against the edge with no inset to absorb the movement. Compounding it, `.ftc-nav-bar` painted at `rgba(10,14,20,0.96)` with `backdrop-filter: blur(16px)` — a translucent bar with a backdrop filter must resample the content behind it every frame of the bounce, and on an SE-class GPU that resample visibly lags the gesture. **Fix (both in `app/globals.css`):** `overscroll-behavior-y: none` on `html` suppresses the document-level bounce (overscroll past the ends only — normal scrolling untouched, `overscroll-behavior` does not inherit, inner scrollers keep native scrolling, so no second scroll container); and a new `.ftc-mobile-nav-bar` rule paints the fixed mobile bar solid with `backdrop-filter: none`. The desktop bar is `sticky`, never rubber-bands, and keeps its blur. **Layout and spacing unchanged on every device** — bar still measures 45px and still carries `pb-[env(safe-area-inset-bottom)]`. Verified in-browser at 375×667 (SE), 390 and 1280: computed `overscroll-behavior-y: none` on html only, mobile bar `rgb(10,14,20)` / no backdrop, desktop bar still `rgba(...,0.96)` + `blur(16px)`, document and inner scrollers both still scroll, no console errors. New regression `testIosOverscrollDoesNotClipFixedChrome`. `npm run build` clean, `npm run test:regressions` pass. Commit `4948a39`.

**iOS fixed-chrome clipping on iPhone SE — root cause identified, fix declined as too costly (2026-08-02):** follow-up to the overscroll commit `4948a39`, which improved the symptom but did not remove it. Isaac confirmed on a physical iPhone SE that the header and bottom nav still "clip/slide under Safari's browser chrome" when scrolling to the very top or bottom. **That phrasing is the tell: this is not rubber-band overscroll at all, it is Safari's dynamic toolbar.**

**Root cause.** The app scrolls the *document* (`document.scrollingElement === document.documentElement`, verified in-browser). On iOS Safari, document scrolling is exactly what drives the collapsing/expanding URL bar and bottom toolbar. As those toolbars animate, Safari resizes the **layout viewport** — but `position: fixed` elements are laid out against that layout viewport (the ICB) and are only re-resolved *after* the toolbar settles, not synchronously with the animation. So mid-transition the fixed bottom nav is still painted at the old layout-viewport bottom, which is now underneath the expanding toolbar. It peaks at the very top and very bottom of a page because that is precisely when Safari restores its chrome to full size. Home-button devices are hit hardest because `safe-area-inset-bottom` is 0, so the bar sits flush to the edge with no inset to absorb the shift.

**This is already documented inside this codebase.** `lib/navigation/prepareFixedChatPageMount.ts` carries the comment *"Event Details uses document scroll; if scrollY persists on return, iOS Safari mispositions `position: fixed` chat chrome above the bottom nav"* — a previous author hit the identical behaviour. Chat pages are immune today precisely because they opt out of document scroll: `lockFixedChatDocumentScroll()` sets `html`/`body` `overflow: hidden`, and `FIXED_CHAT_PAGE_SHELL_CLASS` is a `fixed … h-[100dvh] … overflow-hidden` shell. Every other surface (Events, Gigs, Bookings, Profile, Discover) still document-scrolls and is therefore still exposed.

**Why the previous `overscroll-behavior-y: none` fix could not solve it.** It suppresses rubber-band overscroll *past the ends of the document* — a different mechanism. Safari's toolbar collapse/expand is driven by scroll position and direction, not by overscroll, so removing the bounce cannot stop the toolbar animation or the layout-viewport resize behind it. (Secondary point: `overscroll-behavior` needs Safari 16 / iOS 16+, so on an iPhone SE 1st gen it is ignored outright.) Commit `4948a39` is still a real improvement — it removes bounce-exposure and the per-frame backdrop-filter resample — and should be kept; it just addresses a different mechanism than the one causing the remaining symptom.

**The only complete fix, and why it was declined.** Stop the document scrolling app-wide and move scrolling into an app-shell container — the pattern chat already proves works. If the root scroller cannot scroll, Safari never animates its toolbars, the layout viewport never resizes, and fixed chrome never shifts. **Cost:** Safari's toolbars then stay permanently visible, costing roughly 100px of viewport on an already-small iPhone SE. It also requires real refactoring: `lib/ui/useBodyScrollLock.ts` and `app/(planner-workspace)/calendar/page.tsx` both save/restore via `window.scrollY`, which stops changing once the document is not the scroller; and `body` is `display: flex; flex-direction: column`, so shell children would need `flex-shrink` handling (verified in-browser: a 2500px child shrank to fit and produced no overflow at all, so `body` cannot simply be given `overflow-y: auto`). Isaac reviewed this trade-off on 2026-08-02 and chose to **keep the auto-hiding toolbars and accept the residual clipping** rather than pay ~100px of permanent viewport plus an app-wide scroll refactor.

**Residual known limitation (accepted, not a bug to re-report):** on document-scrolling pages in iOS Safari, fixed/sticky chrome will visibly shift during the toolbar transition at the extreme top and bottom of a page. There is no pure-CSS workaround — `dvh`/`svh`/`lvh` units, safe-area insets and `overscroll-behavior` all describe viewport *size*, none of them change *when Safari re-resolves fixed positioning*. The only lever is not scrolling the document. Revisit only if the ~100px cost becomes acceptable, or if the app moves to a standalone PWA / native shell, where Safari's toolbars do not exist and the problem disappears on its own.

- **Booking acceptance did not propagate to any other view/account — root-caused, fix shipped, NOT YET VERIFIED (2026-08-02, commit `be938e6`):** **Two independent defects, one of which is a database-side prerequisite Isaac must apply.** **(1) `booking_requests` is not in the `supabase_realtime` publication.** Grepped every SQL script: only `message_reactions` and `message_reads` are ever `alter publication supabase_realtime add table`-ed. Postgres emits no replication events for unpublished tables, so the app's *only* booking subscription (`dm-bookings:<conversationId>`, `app/dm/[conversationId]/page.tsx`) has never received a single event since it was written — it subscribes successfully and stays silent, which is exactly why it looked functional. Everything that appeared to update live was local optimistic state (`setBookings`/`setMessages`) in the tab that performed the write — hence planner and Both accounts never updating. Requires `scripts/setupBookingRequestsRealtime.sql`. **(2) The shared Gigs snapshot cache was never invalidated by a mutation.** `updateBookingRequestStatus` only fired the `ftc-notifications-updated` window event, which refreshes *mounted* views; the Gigs list is unmounted while the DJ is in the DM, so module-scoped `memorySnapshot` (gigsListSnapshotPrefetch) survived and the next mount re-read it via `loadGigsListSnapshot({force:false})` — the gig stayed under Incoming with stale counts until a full page load cleared the module. That is the precise mechanism behind "only a hard refresh fixes it", and it is pure client, fixed here. **Acceptance paths do NOT differ** — `BookingRequestCard` renders only in the DM, `updateBookingRequestStatus` has exactly one caller, and the Gigs list has no Accept action at all, so there is a single acceptance path (the DM). **Architecture:** new `lib/bookings/bookingRequestsSync.ts` — one reconciliation entry point `notifyBookingRequestsChanged()` that fans out to registered cache invalidators then re-fires the existing `ftc-notifications-updated` bus (reused, not replaced). Caches *register* invalidators rather than the notifier importing them, because `gigsListSnapshotPrefetch` imports `bookingRequests` and a direct import would close an initialisation cycle. Every status mutation now calls it — accept, decline, rate-proposal accept, and **cancel, which previously did not notify at all** (a related pre-existing gap). `subscribeToBookingRequestChanges` registers on **both** `recipient_id` and `sender_id` (Realtime filters match a single column; the planner is the sender, so a recipient-only filter is why the planner would still miss it even once published), mounted once in `NavBadgeProvider` (renders for every signed-in user on every page) rather than per screen. - **DM repeat-open scroll — FTC QA DJ, actual root cause found and fixed (2026-07-31):** the aspect-ratio and ordering-tiebreaker fixes above were both real and independently correct but did not resolve the reported symptom (confirmed by manual QA after each shipped). Root cause found by live-reproducing the bug in a real, authenticated Chrome tab (Claude in Chrome extension, user's own session — the sandboxed browser-pane tool was confirmed unusable for this: its `ResizeObserver` never fires at all). That reproduction also surfaced an environmental confound worth recording: automation-driven tabs report `document.visibilityState: "hidden"` even while genuinely being screenshotted/interacted with, which throttles `ResizeObserver`/`requestAnimationFrame`/sub-second `setTimeout` delivery almost to nothing — so raw "does the observer fire" timing captured that way is not trustworthy evidence and was discarded in favour of reading `useChatScroll.ts` directly with the reproduction's other findings (scrollTop staying fixed while scrollHeight grows) as a guide. Actual bug: `scrollToBottom()` sets `scrollTop` to the *current* `getChatMaxScrollTop()` and marks `pinnedToBottomRef.current = true`, then calls `container.scrollTo(...)` — the resulting native `'scroll'` event is dispatched *asynchronously* by the browser, never in the same task. If an attachment `<img>` finishes decoding in that gap, `scrollHeight` grows (this never itself fires a `'scroll'` event — appending content below the fold doesn't move `scrollTop`), so by the time the *stale* `'scroll'` event for that earlier `scrollTo()` call finally arrives, `handleScroll()`'s `isNearBottom()` check compares the now-stale `scrollTop` against the new, larger max, sees a gap past the 120px threshold, and wrongly concludes the user scrolled away — clearing `pinnedToBottomRef.current`. The `ResizeObserver` watching the same growth then fires too, but its own re-pin correction reads that same, just-cleared ref and skips correcting, permanently stranding the view short of the true bottom. This explains every symptom across all four rounds: image-heavy only (Breaker Breaker has no post-mount growth to race against), worse on reopen (cached images decode in a tighter burst, widening the race window), and the "visible glitch" reported even on first open (slower network-staggered loading gives more, but not zero, chances to hit the same race). Fix (`lib/useChatScroll.ts`): added `lastAutoScrollTopRef`, set to the target every time `scrollToBottom()` programmatically moves `scrollTop`; `handleScroll()` now returns early — without touching `pinnedToBottomRef` — whenever the event's `scrollTop` still equals that last self-set value, since that means nothing has actually moved and the event is a stale echo of the app's own prior scroll, not user intent. A scrollTop that has genuinely moved (real user scroll, or another effect's own `scrollTo`) is unaffected and still evaluated normally. Regression test: `scripts/test-dm-chat-growth-scroll-race.ts` (wired into `test-regressions.mts`) drives the real hook through exactly this interleaving — deferred `scrollTo` dispatch, growth in the gap, then the stale echo followed by the `ResizeObserver` firing — using a scroll-metrics test double that (unlike the shared harness's) models the browser's async event dispatch instead of firing it synchronously; verified it fails against the pre-fix hook (stuck at the pre-growth position) and passes with the fix (lands on the true post-growth max).
